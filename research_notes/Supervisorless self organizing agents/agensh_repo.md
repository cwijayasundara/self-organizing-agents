## Q1. What problem does Agensh address, and what is its core thesis (why no supervisor)?

### Takeaway
Agensh claims that orchestrator-worker multi-agent harnesses are limited by how much the central orchestrator can plan, assign and integrate. It removes the orchestrator. Identical, equal peer agents run one prompt-defined cooperation loop over three shared infrastructure services: a Git workspace, a chat message interface, and a typed shared-context board. The paper presents "number of agents" as a new scaling dimension, with tests up to 1,024 agents.

### Cited Findings
- Paper title: "Agensh: Scaling Organizational Intelligence to 1,024 Agents". Authors: Zhihao Zhan*, Ting Song*, Li Dong†, Shaohan Huang, Jianxun Lian, Yan Xia†, Furu Wei† (Microsoft Research) — [P](https://github.com/microsoft/Agensh/blob/main/agensh.pdf); [R](https://github.com/microsoft/Agensh/blob/main/README.md)
- Abstract, verbatim: "the scalability of current multi-agent harnesses is often constrained by a central orchestrator's capacity to allocate tasks and coordinate workers. To address this limitation, we introduce Agensh, a scalable self-organized multi-agent harness without a central orchestrator: concurrent workers execute a multi-agent cooperation loop, continuously gathering context, claiming and self-assigning sub-tasks, taking action and sharing findings, verifying results, and merging progress in an asynchronous manner." — [P](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)
- Critique of prior systems: Codex sub-agents, Claude Code sub-agents and agent teams, Copilot fleet and Kimi Agent Swarm "widely adopt an orchestrator-worker structure... This structure usually requires a trained orchestrator to plan and decompose tasks effectively... the scalability of the overall system remains fundamentally limited by the orchestrator's capacity to manage and coordinate its workers and integrate their contributions." It also says Claude Code agent teams are "still organized around a fixed lead session that spawns other agents" — [P](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)
- Motivation for multiple agents: a single agent "is bounded by one context window, one action stream, and one memory stream. The sequential execution constraint imposes high latency" — [P](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)
- README overview: "Agents discover and claim sub-tasks, share findings, verify results and merge progress asynchronously, without a central orchestrator. A shared workspace, message interface and shared context connect each agent's local progress to the team." — [R](https://github.com/microsoft/Agensh/blob/main/README.md)
- Agensh is "an organization harness layered above a single-agent harness rather than a replacement for it". The single-agent harness (GitHub Copilot CLI in the experiments) runs each worker's local agentic loop. Agensh adds identity, cooperation protocols, event routing, dispatch, workspace/messaging/shared-context access, recovery and liveness — [P §2.3](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)
- Related work the paper cites: DeLM (Mao & Mirhoseini, arXiv:2606.10662), the source of the shared-context idea. Carlini's 16-Claude compiler experiment (Git plus task-lock files, no orchestrator). STORM (shared-workspace state management). ChatCollab and SlackAgents. AgentNet — [P §4](https://github.com/microsoft/Agensh/blob/main/agensh.pdf); [board-service README](https://github.com/microsoft/Agensh/blob/main/board-service/README.md)

### Inferences
- The thesis is mainly about engineering and empirical scaling, not theory. Coordination emerges from (a) one fixed prompt protocol plus (b) shared persistent state with push delivery. Nothing is learned or trained.

## Q2. How do agents discover tasks, divide labor, communicate, coordinate, resolve conflicts and terminate without a supervisor?

### Takeaway
Labor division is claim-based self-assignment on a shared board. Each claim is a typed `CLAIM` note with a 1-hour TTL. Collisions are settled by peer-to-peer direct messages. Conflicts are resolved through Git merges: an agent that hits a merge conflict merges `main` back in, re-verifies, and pushes again. There is no voting, bidding or elected leader. Termination is not decided by the agents. An external wall-clock budget (6 h) plus channel reminders at T−45 min and T−5 min end the run, and an idle watchdog prevents agents from stopping early.

### Cited Findings
**The five-step cooperation loop (paper §2.1, verbatim, condensed):**
1. "Gather context. The worker reads the shared user's goal, current state, peer progress and messages, and accumulated findings..."
2. "Claim sub-task. The worker proposes a sub-task to do and announces its scope as a CLAIM appended to the shared context. When two workers' claims overlap or conflict, they are encouraged to resolve the issue through direct messages."
3. "Take action... It also reports intermediate progress through the shared context whenever it establishes findings that may help other workers."
4. "Verify results. The worker matches its local progress against the sub-task's acceptance criteria..."
5. "Merge progress... merging it into the shared workspace. Then it publishes an update describing what is changed, the underlying idea, and verification evidence... If the merge is blocked by a conflict, the worker incorporates the latest peer progress, resolves the conflict, and merges again."

Then "the worker goes back to step 1... By proposing and claiming their own sub-tasks, workers self-organize sub-task discovery and allocation... They proceed asynchronously, allowing each worker to continue without waiting for all peers" — [P](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)

- **The loop lives in the prompt, not in code:** "Agensh realizes the cooperation loop through workflow instructions in each worker's prompt rather than hard-coding the loop into the runtime infrastructure... exactly the same for each worker except for the worker ID." prompts/README adds: "Cooperation is defined by these prompts; the router transports service events and context between native Copilot turns." — [P §2.3](https://github.com/microsoft/Agensh/blob/main/agensh.pdf); [prompts/README](https://github.com/microsoft/Agensh/blob/main/prompts/README.md)
- **Three infrastructure components (paper §2.2):**
  - Shared workspace: Gitea. Each worker has a private checkout and branches and integrates into `main`. Git "detects textual merge conflicts, while hosting issues and pull requests".
  - Message interface: Mattermost. A shared task channel `pbench-task` carries announcements. DMs are for urgent one-to-one messages. "Lower-priority shared-task-channel messages are delivered at the beginning of each loop iteration, while higher-priority direct messages are delivered at the end of each infrastructure tool call."
  - Shared context: a DeLM-style typed board. "New entries on the shared context are treated as higher-priority updates and will be forwarded when every other worker's next infrastructure tool call returns."
  Sources: [P](https://github.com/microsoft/Agensh/blob/main/agensh.pdf); [R](https://github.com/microsoft/Agensh/blob/main/README.md)
- **Task discovery and seeding:** the runner opens one Gitea issue (#1 = the task) with "no assignee; peers self-select". It then sends staggered kickoff DMs (`New task. ${TASK_BRIEF}`) and posts the brief to the channel. Agents "open your own issues for the areas you take, and PRs carry the work" — [scripts/pbench_run.sh](https://github.com/microsoft/Agensh/blob/main/scripts/pbench_run.sh); [AG](https://github.com/microsoft/Agensh/blob/main/prompts/agents.txt); [kickoff.txt](https://github.com/microsoft/Agensh/blob/main/prompts/kickoff.txt)
- **Rule for handling claims that arrive mid-turn (verbatim from AG):** "`FAIL` — stop if you are doing that thing. `FACT` / `OBSERVED` — use it. `CLAIM` on what you are building — a collision; settle it by direct message. any other `CLAIM` — keep building what you are on." — [AG](https://github.com/microsoft/Agensh/blob/main/prompts/agents.txt)
- **When to use DMs versus the channel:** "A direct message on the same server reaches a peer inside their current turn, so it is the fast way to settle a collision — and it interrupts what they are doing. Send a direct message when two of you are about to edit the same thing; use the channel for everything else." — [AG](https://github.com/microsoft/Agensh/blob/main/prompts/agents.txt)
- **Equal peers, minimal coordination:** "N coders, all equal. You claim what to build, you build it, you merge it, and you choose the next thing... Always focus on reproducing the reference; reach for the coordination tools only when your information can greatly impact others' work." — [AG](https://github.com/microsoft/Agensh/blob/main/prompts/agents.txt)
- **Merge policy:** "Agents share the same peer role. Bootstrap allows PR merges with zero required approvals while restricting direct pushes to main; the CI merge gate is disabled." — [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md)
- **Spawning is blocked:** the entrypoint passes `--excluded-tools=task --excluded-tools=list_agents`, so Copilot's native sub-agent tools are removed. A deny list also removes many Gitea/Mattermost tools, such as `create_repo`, `create_branch`, `create_or_update_file`, `get_file_contents`, `create_channel` and `delete_message`. Agents use the git CLI for code — [agent/entrypoint.sh](https://github.com/microsoft/Agensh/blob/main/agent/entrypoint.sh); [copilot-deny-tools.json](https://github.com/microsoft/Agensh/blob/main/agent/config/copilot-deny-tools.json)
- **Verification:** each worker checks its own work. AG step 4 says: "Check your work by running the reference and your build on the same inputs and comparing." The board's server-side "verifier" is only a "deterministic text check; it does not execute the claimed tests". It rejects a PATCH_SUMMARY whose `evidence=` is missing or starts with one of: tbd, pending, not verified, unverified, should work, should pass, looks right, looks correct, seems to work, to be verified, will verify, n/a — [board-service/verifier.py](https://github.com/microsoft/Agensh/blob/main/board-service/verifier.py)
- **Termination and liveness (external):**
  - Budget: "At T = t + 6 h, all agents are terminated and the submission is exported" (export of committed Git HEAD of main).
  - Channel reminders, verbatim. deadline-45m: "@all **45 minutes left.** Stop dispatching new features. From here the only goal is that root `compile.sh` builds `./executable` and that everything already written is merged to the default branch. Land the open PRs; work that is not merged does not count. If a PR cannot be merged, say so and move on." deadline-5m: "@all **5 minutes left.** Merge anything that is ready right now, then stop. Confirm root `bash compile.sh && ./executable` still works on the default branch and post the final state."
  - Idle nudge after 600 s of inactivity, checked every 60 s, repeat interval 600 s, skipped if events are already queued. Text (idle.txt): "There is always new work — do not be bounded by the previous CLAIMs' scope: pick up /opt/pbench/executable, run it against untried inputs, and close the gap between reference and the team's implementation."
  Sources: [P App. C](https://github.com/microsoft/Agensh/blob/main/agensh.pdf); [prompts/](https://github.com/microsoft/Agensh/tree/main/prompts); [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md); [pbench_run.sh](https://github.com/microsoft/Agensh/blob/main/scripts/pbench_run.sh)
- **Forced-publication nudge:** after each completed turn, the dispatcher compares the agent's latest own gist ID before and after the turn. If the agent wrote nothing, it sends "==== SHARED CONTEXT: ANYTHING TO PUBLISH? ==== This turn produced no board entry. If you established something your peers can build on, publish it now; if you are still mid-task, refresh your `CLAIM`... Do NOT publish a placeholder. Publish only evidence — let peers draw their own conclusions." — [mini-router/src/dispatcher.ts](https://github.com/microsoft/Agensh/blob/main/mini-router/src/dispatcher.ts); [board_client.ts](https://github.com/microsoft/Agensh/blob/main/mini-router/src/board_client.ts)
- **Staggered activation reduces scope contention:** "launching one agent every 30 seconds during the first hour and one every 3 seconds thereafter". Defaults are `PBENCH_WAKE_STAGGER_S=30`, `PBENCH_WAKE_FAST_STAGGER_S=3`, `PBENCH_WAKE_RAMP_SUBJ_S=3600`, plus a 20 s settle and a ≥60 s wait. "Later workers get less time." — [P App. C](https://github.com/microsoft/Agensh/blob/main/agensh.pdf); [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md)

### Inferences
- Agensh uses no bidding, auction, voting or consensus protocol. Mutual exclusion is advisory and optimistic: claims are visible but not locked, they expire, and real conflicts appear at Git merge time. Rules for a LangChain Deep Agents port would be: identical agents; a shared typed board with TTL claims; push delivery of peer notes into tool results; a shared VCS-like workspace with merge conflicts surfaced to the agent; external clock and idle nudges for liveness. No agent should get a "task"/sub-agent tool.
- The forced-write nudge text says "your lead", but the system has no lead. This looks like leftover wording.

### Gaps
- The repo does not describe any mechanism for agents to decide on their own that the goal is "done". Termination is purely budget-driven in the released benchmark setup.

## Q3. What are the core abstractions and components? Repository map.

### Takeaway
The repo is infrastructure plus prompts. Components: a per-worker Docker image wrapping Copilot CLI over ACP; a per-worker TypeScript "mini-router" sidecar for event ingestion, a durable queue and serialized turns; a FastAPI "board-service" for shared context, exposed to agents as MCP tools; Gitea and Mattermost; a token secret-service; and bash/Python launch and scoring tools.

### Cited Findings
- Top-level layout (from the git tree): `agent/` (Dockerfile(s), `acp-bridge.py`, `archive.py`, `entrypoint.sh`, `config/mcp.json.tmpl`, `config/copilot-deny-tools.json`); `board-service/` (`main.py`, `shared_lessons.py`, `verifier.py`, `gquery.py`, `unfold.py`, `mcp.cjs`); `mini-router/` (TS: `main.ts`, `dispatcher.ts`, `state.ts`, `acp_socket_channel.ts`, `board_client.ts`, `group_messages.ts`, `listeners/gitea/*`, `listeners/mattermost/*`, `uem.ts`, `uem_render.ts`; `mcp-notice-shim.cjs`; `sql/01-events-schema.sql`, `02-mattermost-db.sql`, `03-board-schema.sql`); `prompts/`; `scripts/` (`launch_single_node.sh`, `pbench_run.sh`, `pbench_chain.sh`, `launch_single_agent.py`, `acp_driver.py`, ...); `secret-service/`; `docker/` (compose, bootstrap, nginx-edge, systemd slice and guard); `tools/` (`gen-compose-prod.py`, `pbench_submission.py`, `pbench_score_report.py`); `demo/`; `agensh.pdf` — [git tree API](https://api.github.com/repos/microsoft/Agensh/git/trees/main?recursive=1)
- RP component table: "Worker image, Copilot and shutdown archives | agent/; Shared context and work claims | board-service/; Event routing and messaging | mini-router/; Bootstrap-issued worker tokens | secret-service/; Compose, provisioning and host guards | docker/; Runtime instructions and launch messages | prompts/; Launch and lifecycle scripts | scripts/; Compose generation, submission export and scoring | tools/" — [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md)
- **Shared context board data model.** `VALID_TYPES = ("FACT", "OBSERVED", "FAIL", "CLAIM", "PATCH_SUMMARY")`, `MAX_CONTENT_CHARS = 100`, `MAX_PATCH_SUMMARY_CHARS = 300`, `MAX_BOARD_ENTRIES = 2000`, `DEFAULT_CLAIM_TTL_SECONDS = 3600`. MySQL table `board_gists(id, board_id, thread_id, type, content, ts_epoch, expires_at, delegation_id, detail LONGTEXT)` is append-only. Each gist gets a label `G<id>`. — [shared_lessons.py](https://github.com/microsoft/Agensh/blob/main/board-service/shared_lessons.py); [03-board-schema.sql](https://github.com/microsoft/Agensh/blob/main/mini-router/sql/03-board-schema.sql)
- **Board semantics** (shared_lessons.py and board README):
  - A PATCH_SUMMARY with the same (author `thread_id`, `delegation_id`) REPLACES the author's earlier one in the recent view.
  - "A matching `FAIL` invalidates that author's latest candidate", which sets status `invalidated` and `local_failures=N`.
  - A PATCH_SUMMARY is marked `verified` only if its evidence avoids weak words (pending/should/looks/seems/tbd...) and matches `pass(ed|es)?|verified|confirmed|no longer|now returns|now produces`.
  - Claims are hidden after the TTL, but history is kept for grep.
  - Exact-text dedup, plus "semantic" dedup that only triggers on strong code anchors (file+symbol, file+line, test names, error names). Duplicates render as `(xN)`.
  Sources: [shared_lessons.py](https://github.com/microsoft/Agensh/blob/main/board-service/shared_lessons.py); [board README](https://github.com/microsoft/Agensh/blob/main/board-service/README.md)
- **Prompt render format.** Lines look like `[t<agent>/<TYPE> +<min>m] content`. Claims add `, +X.Ym left`. Patches add ` [status=verified,invalidated,local_failures=N]`. Sections are ordered: "[Patch summaries — candidate fixes proposed by peer threads; review BEFORE deciding to submit or to propose your own]", "[Active claims — peer threads' current targets; pick a different angle if your plan duplicates theirs]", "[Shared lessons]". The whole block is wrapped in `==== SHARED CONTEXT ====` ... `==== END SHARED CONTEXT ====` and followed by guidance: "The entries above are verified notes published by your peers. Read them BEFORE acting: do not re-derive a FACT someone already established, do not repeat a path recorded as FAIL, and check PATCH_SUMMARY entries before proposing your own fix." Empty board: "Nothing has been published yet... publish concrete findings rather than plans." — [shared_lessons.py](https://github.com/microsoft/Agensh/blob/main/board-service/shared_lessons.py); [board_client.ts](https://github.com/microsoft/Agensh/blob/main/mini-router/src/board_client.ts)
- **Board MCP tools** (mcp.cjs):
  - `board_read(board_id)` returns the whole recent board, newest 2000.
  - `board_write(board_id, type, content, detail?, delegation_id?)`. PATCH_SUMMARY format: `"files=A/B/C | idea=D | evidence=E | risk=F"`. `delegation_id` is described as: "The unit of work this note belongs to — a short label for the sub-task you are on, e.g. "python-parser". Reuse the SAME id for every note about that sub-task: a refined PATCH_SUMMARY then REPLACES your earlier one... and a FAIL strikes your own patch summary. A fresh id per note silently disables both."
  - `board_grep(board_id, words?, limit?=500, types?)` searches full history with `|` OR, `&` AND and `()` grouping, and reports "showing N of M".
  - `board_unfold(board_id, labels[])` expands `G12` style labels into full `detail` text.
  Sources: [board-service/mcp.cjs](https://github.com/microsoft/Agensh/blob/main/board-service/mcp.cjs)
- **Board HTTP API:** `GET /snapshot` (unread context, advances viewer cursors), `GET /board/{id}/read`, `/read_all`, `/grep`, `/unfold`, `POST /board/{id}/note`, `GET /pending/{agent}` (lease new DMs and unread peer gists), `POST /shown/{agent}`, `POST /board/{id}/lifecycle` — [board README](https://github.com/microsoft/Agensh/blob/main/board-service/README.md)
- **Mid-turn push (mcp-notice-shim).** Every MCP server (gitea, mattermost, board) runs behind `mcp-notice-shim.cjs`. On each `tools/call` result, it leases pending DMs and peer gists from `/pending/{agent}`, appends their text to the tool result, and reports them `shown`. "This path operates on MCP tool returns; it does not interrupt an arbitrary running process." — [mini-router README](https://github.com/microsoft/Agensh/blob/main/mini-router/README.md); [mcp.json.tmpl](https://github.com/microsoft/Agensh/blob/main/agent/config/mcp.json.tmpl); [P App. B.2](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)
- **Event router.** Listeners for Gitea SSE/REST and Mattermost WebSocket/REST normalize activity into "unified event messages" (UEM) in a MySQL queue with per-agent dedup. The dispatcher serializes turns: batches of up to 32 events, board snapshot prepended as a prompt prefix, ACP prompt, ack on turn completion. Delivery states are `pending → sending → sent`, plus `failed → retrying`. Delivery gives up after 5 attempts. A restart returns `sending` rows to pending. Group-message backlogs over 32 are spilled to JSONL files. The ACP silence watchdog is 20 min (`MINI_ROUTER_STUCK_MS=1200000`). Event format shown to agents: `[event] event_id=... source=... kind=... observed_at=... summary: ...` — [mini-router/src README](https://github.com/microsoft/Agensh/blob/main/mini-router/src/README.md); [dispatcher.ts](https://github.com/microsoft/Agensh/blob/main/mini-router/src/dispatcher.ts); [AG](https://github.com/microsoft/Agensh/blob/main/prompts/agents.txt); [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md)
- **Harness adapter.** The paper says Agensh "can connect to different underlying harnesses, such as Claude Code and Copilot, through lightweight harness-specific adapters". The released code uses Copilot 1.0.70 over ACP (`acp-bridge.py`, `@agentclientprotocol/sdk`) — [P](https://github.com/microsoft/Agensh/blob/main/agensh.pdf); [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md)

### Inferences
- How the pieces map to Deep Agents (my inference): board → a shared store (DB) with the four tools above; mcp-notice-shim → tool-call middleware/wrapper that appends peer notices to every tool result; router/dispatcher → an outer event loop per agent that builds each new turn from queued events plus the board snapshot; Gitea → a shared git repo or a file store with optimistic merge.

### Gaps
- The released code contains no Claude Code adapter. Only Copilot is present.

## Q4. What does REPRODUCE.md say: benchmarks, models, agent counts, metrics, results, compute/cost, commands?

### Takeaway
The benchmark is ProgramBench (Meta/FAIR, v1.2.5 pinned): rebuild a program from black-box execution of its binary plus bundled docs, offline, within 6 h. The five hardest tasks were used, with GPT-5.6-sol at high effort via Copilot, with 1/8/32/128 agents (1,024 on pandoc only). Mean pass rate rose 19.31% → 28.78%. Per-task scaling is non-monotonic. No dollar or token cost is reported.

### Cited Findings
- Defaults: "8 workers, 6 hours per task, `gpt-5.6-sol`, high reasoning effort, the Responses API and a 272,000-token prompt window". The paper says max output is 128,000 tokens — [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md); [P App. C](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)
- Tasks: `jgm__pandoc.5caad90`, `gromacs__gromacs.665ea4c`, `universal-ctags__ctags.243595e`, `php__php-src.c891263`, `ffmpeg__ffmpeg.360a402`. These are the hardest of ProgramBench's 200 by mean SOTA pass rate. Reference repo sizes: FFmpeg 10,090 files / 1.55M LOC; gromacs 815k LOC; pandoc 104k LOC; PHP-src 2.81M LOC; ctags 246k LOC — [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md); [P Table 1](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)
- Metric: ProgramBench "canonical-kept pass rate" (final hidden-test pass rate). It is computed with `tools/pbench_score_report.py` — [P App. C](https://github.com/microsoft/Agensh/blob/main/agensh.pdf); [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md)
- Mean results across 5 tasks: 1 agent 19.31%; 8 agents 20.68%; 32 agents 26.52%; 128 agents 28.78% (+9.47 pp, ≈49% relative) — [P §3.1](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)

- README-only claim (not in the v1 paper): "With the latest GPT-6.1-sol at high reasoning effort, the six-hour Pandoc test-pass rate rises from 56.19% with 1 agent to 79.59% with 32 agents, a relative improvement of 41.64%." — [R](https://github.com/microsoft/Agensh/blob/main/README.md)

Let's make the 6h fulfilled." — [P App. C](https://github.com/microsoft/Agensh/blob/main/agensh.pdf); [scripts/launch_single_agent.py](https://github.com/microsoft/Agensh/blob/main/scripts/launch_single_agent.py)
- Key commands: `bash scripts/pbench_gen_env.sh`; `JOBS=1 bash scripts/pbench_build_pertask_images.sh`; `PREFLIGHT_ONLY=1 bash scripts/launch_single_node.sh`, then `setsid nohup bash scripts/launch_single_node.sh > out/single-node.launch.log 2>&1 < /dev/null &`; `python3 scripts/launch_single_agent.py --config baseline.json`; `uv run --project "$PROGRAMBENCH_REPO" python tools/pbench_score_report.py "$RUN_DIR" "$TASK_ID"`; `make down|clean PROFILE=...`. - Compute and infrastructure: Linux, Docker Compose v2, systemd, cgroup v2, passwordless sudo. Workers have a 64 GiB memory ceiling and routers 8 GiB. The `pbench.slice` caps team containers at 80% of host RAM. Workers run as UID 10000 and can execute but not read the reference binary (mode 0111). The network allows only model egress. For large teams, raise `MM_MAX_USERS_PER_TEAM` (default 200) and review `MYSQL_MAX_CONNECTIONS` (default 1,000; "each router can use four connections") — [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md)
- Release caveats: the release pins Copilot 1.0.70 and Mattermost MCP 0.5.1 and uses the v6 cleanroom, while "The historical main experiment seeded the older `task_cleanroom` reference... a new release run should record its own revision rather than claim exact historical reproduction." ### Inferences
- Gains depend heavily on the task. ctags falls at 8 agents (25.82 → 18.47), gromacs is flat until 128, and FFmpeg drops slightly from 32 to 128. The headline mean hides this variance. Each configuration appears to be a single run, since no error bars or seeds are reported.

### Gaps
- The sources give no token usage, API cost or GPU/CPU-hours. The multi-node orchestration for 1,024 agents is not in the release. Variance across repeated runs is not reported.

## Q5. Which prompts drive self-organization? Any role or persona templates?

### Takeaway
There are NO role or persona templates. Every agent receives the same `agents.txt` prompt (identity, services, work cycle, rules for handling board events) concatenated with the task brief. The only difference is the worker ID. The paper says roles (reviewer, integrator) emerge rather than being assigned.

### Cited Findings
- "The complete worker prompt is presented in Appendix A, which is exactly the same for each worker except for the worker ID." Appendix A reproduces it for `pbench-team1-worker1` with "You work with 1024 peers" — [P](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)
- Prompt files: `agents.txt` (identity, services and the observe/claim/build/verify/merge/publish cycle), `pbench-brief.txt` (objective, offline rules, `compile.sh` contract), `task-brief.txt` (IDs), `kickoff.txt`, `idle.txt`, `deadline-45m.txt`, `deadline-5m.txt`, `single-agent/{brief,rules,resume}.txt`. `entrypoint.sh` expands `agents.txt` with `${AGENT_NAME}`, `${PBENCH_WORKERS}`, `${GITEA_ORG}` and `${PBENCH_BRIEF}` into `/work/AGENTS.md` — [prompts/README](https://github.com/microsoft/Agensh/blob/main/prompts/README.md)
- Work cycle in AG, verbatim: "1. Run `/opt/pbench/executable` to observe the unexplored areas to build. 2. Announce the area you are taking as a `CLAIM` on the shared context board. 3. Run `/opt/pbench/executable` on that area under `ulimit -v 67108864` and write code that reproduces what you observe, based on current `main`. You do not need to sync code with others during implementation. 4. Check your work by running the reference and your build on the same inputs and comparing. 5. Push, open a PR, and merge to `main`. If the merge is refused, merge the latest `main` into your branch, re-check your work against the reference, and push again. 6. Say what you finished as a `PATCH_SUMMARY` (`files= | idea= | evidence=`) on the board, then go back to 1." Also: "**Anything else.** MCP, git CLI, shell, curl, writing files — whatever is at hand is fine. If the tool you have is not enough, look for one; if there is none, build one." — [AG](https://github.com/microsoft/Agensh/blob/main/prompts/agents.txt)
- Board-writing guidance in AG: "Publish with `board_write` the moment you establish something — `OBSERVED` for noticeable reference behaviour, `FACT` for what you confirmed, `FAIL` for a hypothesis you falsified (the highest-value entry: it stops peers spending budget on it), `PATCH_SUMMARY`... and `CLAIM` while you are working so peers pick a different angle... Do not re-derive a peer's `FACT`, and do not retry something recorded as `FAIL`." — [AG](https://github.com/microsoft/Agensh/blob/main/prompts/agents.txt)
- Autonomy rule (pbench-brief): "**Fully autonomous**: the whole team defines requirements itself, breaks down work itself, decides itself, and finishes itself. There is no external input; do not wait for instructions, do not ask on mattermost "what to do next" — the answer is always: **push the rebuild forward**." — [pbench-brief.txt](https://github.com/microsoft/Agensh/blob/main/prompts/pbench-brief.txt)
- Emergent behaviour reported at each scale (paper §3.2, from trajectories):
  - 8 agents: peers agree on interfaces, and overlaps get resolved (in FFmpeg, one worker switched scope).
  - 32 agents: multi-worker review and integration; in PHP-src, an approval was withdrawn after a peer found a counterexample.
  - 128 agents: "Workers are choosing reviewers based on relevant prior experience and reuse these review relationships". In pandoc, a standardized protocol emerged: the author updates and tests a branch, sends its commit hash, and a peer validates and merges. It was later revised to give the peer the whole update/test/check/merge cycle.
  - 1,024 agents: "multiple workers served as integrators. A worker could contact several candidate integrators, select the first valid responder, cancel the other requests"; same-area specialists took over failed work.
  Source: [P](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)

### Inferences
- The emergent roles are qualitative anecdotes from trajectories. The paper does not quantify how often they occur.

### Gaps
- The released repo does not include trajectories or a role-frequency analysis to check the emergence claims. The project-page replay (agens-harness.github.io) was not examined.

## Q6. Which failure modes, limitations or ablations are reported?

### Takeaway
The paper has no ablation study and no limitations section. I found no ablation of the board, DMs, delivery priority or claim TTL. Limitations are visible only indirectly: non-monotonic per-task results, operational caveats in REPRODUCE.md, and the extra mechanisms the harness needs (forced-write nudge, idle watchdog, staggered start, deadline reminders).

### Cited Findings
- The paper's sections are Intro, Harness, Scaling Results, Emergent Cooperation, Related Work, Conclusion and Appendices A–C. There is no ablation or limitations section — [P](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)
- Non-monotonic per-task scaling (ctags drop at 8 agents, FFmpeg 13.22 → 12.89 from 32 to 128, gromacs flat 19.69 → 19.37 → 19.37 → 22.12) — [P Fig. 5](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)
- Scope contention is reduced by stagger: "To reduce scope contention, we stagger agent activation". "Actual startup can exceed those targets; later workers get less time. The ramp can overrun the budget" — [P App. C](https://github.com/microsoft/Agensh/blob/main/agensh.pdf); [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md)
- Liveness problems the harness works around: "a single-agent run can rarely sustain the full 6-hour runtime" (hence the stop hook); idle detector at 10 min; ACP silence watchdog at 20 min; a forced-write nudge when an agent publishes nothing — [P App. B–C](https://github.com/microsoft/Agensh/blob/main/agensh.pdf); [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md)
- The board "verifier" does not execute tests, only text heuristics: "The service checks text deterministically, without running the verification commands an agent reports." — [board README](https://github.com/microsoft/Agensh/blob/main/board-service/README.md)
- Mid-turn push only reaches an agent at MCP tool-call boundaries ("does not interrupt an arbitrary running process") — [P App. B.2](https://github.com/microsoft/Agensh/blob/main/agensh.pdf)
- Scaling limits on infrastructure: Mattermost max users per team (default 200) and MySQL connections (default 1,000, four per router) must be raised by hand — [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md)
- Evaluation pitfalls: "ProgramBench can exit zero with incomplete branches"; the chain's `SCORE` line "counts raw attempts" rather than the canonical score — [RP](https://github.com/microsoft/Agensh/blob/main/REPRODUCE.md)

### Inferences
- Communication overhead is controlled by design: 100/300-char caps, a `detail` field you unfold on demand, a 2000-entry recent window plus grep, claim TTL, dedup, and AG's instruction to use coordination tools "only when your information can greatly impact others' work". The paper does not measure that overhead. Merge-conflict rates are also unreported.
- Compute cost grows roughly linearly with agent count, since each agent is a full GPT-5.6-sol session for 6 h. Under that assumption, 128× cost bought +9.47 pp on the mean. The paper does not discuss cost-efficiency.

### Gaps
- There are no ablations: board on/off, DM priority, claim TTL, identical prompts versus role prompts, or an orchestrator baseline at equal agent count. The authors compare only against a single agent, not against an orchestrator-worker system with the same number of agents.
